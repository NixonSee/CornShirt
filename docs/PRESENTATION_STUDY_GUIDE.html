Next.js App Router

How folders and special files become pages and APIs.

CornShirt uses file-system routing under src/app. Folder names create URL segments; special filenames decide what the route does.

FileJob
page.tsxDefault React component that renders UI at the folder URL.
layout.tsxWraps a route subtree; CornShirt uses role layouts for page protection and shared UI.
route.tsExports HTTP handlers such as GET, POST, PUT, or DELETE.
not-found.tsxRenders a route-specific missing-resource state.
Key defence: Routing selects code. It does not prove identity, role, ownership, or valid state. Protected handlers repeat those checks.
02

route.ts vs page.tsx

They claim routes for different purposes.

page.tsx

Called by navigation or <Link>. Usually returns JSX/React UI. Example: src/app/events/[eventId]/page.tsx.

route.ts

Called through HTTP, usually by fetch or a webhook. Returns Response/NextResponse. Example: checkout POST.

File extension reminder:
.tsx = TypeScript file that can contain JSX/React UI.
.ts = TypeScript file without JSX.
JSX is HTML-like syntax used inside React components to describe what UI should appear.

Replacing the checkout handler with page.tsx removes the expected POST API. Replacing the event page with route.ts produces an endpoint instead of rendered UI. A page guard improves navigation, but an API route remains the security boundary for mutations.

03

Why folders contain [id]

One route handles many real resources.

The folder name [id] is used for dynamic routing, and it loads the specific data identified by that URL value. In CornShirt, that data could be a particular event, ticket, listing, user, or operation.

Square brackets create one dynamic URL segment. CornShirt uses descriptive names such as [eventId], [ticketId], [listingId], and [operationId].

src/app/events/[eventId]/page.tsx
URL: /events/abc-123
params: Promise<{ eventId: string }>
const { eventId } = await params;

Changing [eventId] to [id] still matches the same URL shape, but code must read params.id. Removing brackets makes eventId literal. Knowing an ID never grants permission; the backend still checks ownership.

04

Data Transfer Objects

The safe shape crossing a system boundary.

DTO = selected and structured data sent between the frontend and backend.

CornShirt uses , , , and —not DTO classes. Select any term to see its meaning and example.

A DTO defines:

  • What data should be sent.
  • What fields are required.
  • What type each field should be.

Example:

type CreateEventDTO = {
  title: string;
  venueId: string;
  startDate: string;
  description: string;
};
Why not cast? Casting only tells TypeScript that we assume the data type is correct, but it does not validate the real incoming data. A DTO defines the expected data structure, and validation checks that the frontend data actually matches it before the backend uses it.

06

Solidity error: require or if/else?

Invalid transaction versus valid alternative branches.

require(condition, "message") stops execution and reverts all transaction state when the condition is false. A plain if/else only chooses a branch and does not automatically fail.

require(priceInSen > 0, "Invalid price");

// Equivalent guard style with a custom error:
if (priceInSen == 0) revert InvalidPrice();

Use if/else when both branches are valid behaviors. Use require or explicit revert when failure must cancel the transaction. A Next.js handler can use if (!valid) return NextResponse.json(...) because it returns an HTTP error; Solidity has no HTTP response.

High-frequency syntax
07

_functionName, ?function, !function and related forms

What these forms really mean in TypeScript and Solidity.

_name
The underscore is part of the identifier, not an operator. In Solidity it conventionally marks internal/private implementation details. CornShirt calls inherited _grantRole, _safeMint, and _burn, and stores _nextTokenId. The actual declaration—not the underscore—enforces visibility.
name?: T
An optional TypeScript property or parameter. Example: onSelectZone?: (id: string | null) => void. The value may be undefined.
fn?.()
Optional call. onSelectZone?.(zone.id) calls only when the function exists. A standalone ?function is not normal JavaScript syntax.
obj?.value
Optional chaining. Read deeper only when the left side is not null/undefined, as in venueData?.layout?.stage.
a ?? b
Nullish fallback. Use b only when a is null or undefined. It preserves valid 0, false, and empty strings.
!value
Logical NOT. if (!auth.ok) means “if authorization is not successful.” It converts truthy/falsy and reverses the Boolean.
value!
TypeScript non-null assertion: tells the compiler the value exists. It performs no runtime check and can hide a bug. Prefer real validation where possible.
!= / !==
Inequality. Prefer strict !== in TypeScript because it does not coerce types. Solidity comparisons are statically typed.
test ? a : b
Ternary expression for one compact two-result choice. CornShirt uses it for labels and JSX. Avoid deeply nested ternaries.
() => {}
Arrow function, often used for callbacks and React state updates. A declared function name() is often clearer for major named operations.
...value
Spread copies array/object members; rest collects remaining values. React state updates use spread to create a new object instead of mutating the old one.
as Type
Compile-time assertion. It does not validate runtime input. as const preserves literal values and readonly intent.
A | B
Union type: a value may be one of several known types/states. Workflow action unions make impossible combinations harder to express.
unknown
Safer than any for external data because code must narrow or validate before use.
@/...
Project import alias for the src directory, such as @/lib/requireRole.
Presentation rule: say the complete form. “Question mark” could mean optional property, optional chaining, optional call, ternary, or part of ??. “Exclamation mark” could mean logical NOT, non-null assertion, or inequality.
08

Decision or repetition?

Choose the construct that matches the job.

  • if/else: one condition selects behavior.
  • switch: one value has several exact cases, such as role → home route.
  • for/for...of: repeat work, especially with early break or sequential await.
  • map: transform every item.
  • filter: keep every matching item.
  • find: return the first match.
  • reduce: combine into one value.
  • slice: take a non-mutating subsection.

A loop cannot replace a one-time decision. One if cannot filter an entire event collection unless it is itself inside repetition.

09

async, await, and Promise.all

Order independent work safely.

An async function returns a Promise. await pauses that function until the Promise settles.

  • Use Promise.all for independent reads such as loading profile and wallet rows.
  • Use sequential await when step two needs step one: reserve inventory → create Stripe Session.
  • Use sequential blockchain steps: approve NFT → confirm approval → create listing.
Parallelizing dependent work can charge before reservation, list before approval, or process data that does not yet exist.

Frontend

UI + routing
10

.ts vs .tsx

The difference is JSX syntax, not frontend versus backend.

.ts contains TypeScript without JSX: business rules, validators, database helpers, Stripe logic, and route handlers. .tsx is TypeScript that may contain React markup such as <Button>.

Examples: src/lib/currency.ts has logic; EventTicketing.tsx renders interactive ticket UI. A route.ts is usually .ts because it returns HTTP responses, not JSX.

11

Components, props, state, and hooks

Know what comes in, what changes, and what is derived.

  • Component: function returning UI.
  • Props: parent-provided input, such as event and isCustomer.
  • State: changing local UI memory, such as selectedTicketTypeId.
  • Derived state: calculated from existing props/state; do not duplicate it unnecessarily.
  • useEffect: synchronize with fetch, timers, camera, or other external systems.
  • useMemo: cache a derived calculation; not security.
  • useRef: preserve mutable values without re-render, such as an idempotency key.

"use client" is required for browser state, effects, click handlers, camera, and browser APIs. Server Components can securely load data and keep secrets off the client.

Part II

Backend

The trusted coordinator for Auth, Supabase, Stripe, wallets, blockchain, email, and safe HTTP responses.

Security + services
13

Authentication and authorization

Who are you, and what may you do?

  • proxy/updateSession: maintain cookie-backed Supabase session.
  • getVerifiedRole: verifies Auth user and loads trusted profiles.role/status.
  • requireRole: protects pages with redirects.
  • authorizeApiRole: protects APIs with 401/403 responses.

Layouts make navigation safe and friendly; API guards secure data and mutations against direct HTTP calls.

14

Validation and early returns

Reject bad requests before side effects.

authorize→parse→normalize→validate→load truth→check owner/state→side effect
if (!auth.ok) return auth.response;
if (!body) return NextResponse.json({ error }, { status: 400 });

Early returns keep the success path flat. Browser checks are repeated because clients can be bypassed.

15

Supabase clients and trust

Use the correct credential for the correct boundary.

  • Browser client: anonymous key; follows RLS.
  • Server session client: request cookies; user-scoped server work.
  • Admin client: service role; bypasses RLS and must remain server-only.
Importing supabaseAdmin or a wallet private key into client code exposes privileged authority.
16

Idempotency and recovery

Retries resume instead of repeating money or asset movement.

CornShirt stores idempotency keys, Stripe IDs, webhook claims, blockchain hashes, and workflow states. It records a transaction hash immediately after submission and before waiting for the receipt, so a crash can recover the original result.

claimStripeEvent prevents duplicate webhook work; recoverMintResult decodes the prior mint; processed Marketplace payment hashes prevent replay.

20

Security concepts

Every check protects a named risk.

  • Least privilege: separate minter, burner, and settler roles.
  • Approval: Marketplace cannot move the seller’s NFT without permission.
  • Checks-effects-interactions: update state before external NFT call.
  • nonReentrant: blocks nested protected execution.
  • processedPayments: one payment reference settles once.
  • safeTransferFrom: rejects incompatible contract recipients instead of trapping NFT.
21

Mapping, array, struct, and events

Storage choices match how data is accessed.

A mapping gives direct lookup when the listing hash is known; an array would require a loop whose gas grows. A Listing struct keeps seller, token, price, expiry, and active state together. Mappings are not naturally enumerable, so Supabase supplies the browsable marketplace catalogue. Contract events record history; mappings store current state.

23

Keys, constraints, indexes, RLS

Database rules remain correct under concurrency.

  • Primary key uniquely identifies a row.
  • Foreign key blocks orphan references.
  • Unique constraint prevents duplicate active listing/token/workflow states even when requests race.
  • Index speeds intentional lookups but adds write/storage cost.
  • RLS limits browser-visible rows; trusted admin code bypasses RLS and must authorize explicitly.

Two TypeScript requests can both read “none found.” PostgreSQL uniqueness still prevents both conflicting inserts from committing.

Cross-layer

End-to-end workflows

Trace the real order across browser, API, database, Stripe, blockchain, and email.

Explain aloud
27

Primary purchase

  1. UI sends event/type/stable key.
  2. API authorizes and validates DTO.
  3. RPC reserves inventory and price.
  4. Stripe Checkout is created/reused.
  5. Signed webhook verifies exact payment.
  6. NFT mint is submitted/confirmed.
  7. RPC finalizes ticket, QR, transaction.
  8. Email is attempted idempotently.
28

Direct transfer

  1. Authorize sender and validate recipient.
  2. Check ticket state, transfer policy, wallet readiness.
  3. Compare database owner with ownerOf.
  4. Fund gas if below threshold.
  5. Sign safeTransferFrom.
  6. Confirm receipt and atomically update ownership/history.
29

Marketplace resale

  1. Seller ownership and 15% cap checked.
  2. NFT approval confirmed before listing.
  3. Buyer reservation prevents double sale.
  4. Stripe webhook proves payment.
  5. Settler moves existing NFT—no mint.
  6. RPC finalizes owner/listing/proceeds.
30

Cancellation and refund

  1. Event cancellation changes eligibility.
  2. Latest payer may differ from current owner after free transfer.
  3. Stripe refund is created exactly once.
  4. Authorized burner destroys surrendered NFT.
  5. RPC reconciles ticket/accounting/operation.
  6. Claim and webhook workers safely race.
31

QR verification

  1. Scanner pauses repeated frames.
  2. Verify endpoint checks organizer/event/ticket/status/QR.
  3. On-chain ownership is compared when applicable.
  4. Organizer explicitly confirms entry.
  5. Use endpoint atomically marks used and logs attempt.

Hiding a QR in UI is convenience, not security.

32

Event lifecycle

Organizer creates pending event with authoritative venue zones. Admin approves/rejects. Active events are sellable until three hours after start. complete_finished_events completes events and expires related actions consistently. The NFT can remain as a collectible after operational expiry.

Practice

Project-code Q&A

Answer before opening the panel. Strong answers mention the named file/function and the failure prevented.

Easy → difficult
33
Easy

Routing and syntax

Why is EventTicketing.tsx not .ts?
It renders JSX and manages React interaction. Plain .ts is sufficient when no JSX syntax exists.
What URL does events/[eventId]/page.tsx match?
One dynamic segment such as /events/abc-123; Next.js supplies params.eventId.
What does onSelectZone?.(zone.id) mean?
Optional call: invoke the callback only if it is defined. The ?. prevents an error when the optional prop is absent.
Does the underscore in _safeMint make it private?
No. It is a naming convention. The inherited function declaration controls visibility; OpenZeppelin declares this implementation helper for internal use.
34
Medium

Application decisions

Why does parseTicketCheckoutBody accept unknown?
HTTP JSON is untrusted runtime data. unknown forces checks before field use; a TypeScript cast alone cannot prove the real shape.
Why does filterEvents use filter instead of one if/else?
It must test every event and return all matches. filter expresses a collection operation; one if expresses one decision.
Why are both requireRole and authorizeApiRole needed?
Pages need redirects for navigation; APIs need 401/403 responses and must resist direct requests. Page protection alone cannot secure a mutation.
Why use integer sen?
Stripe uses minor units and integer arithmetic avoids floating-point currency errors. The server derives the amount rather than trusting display price.
35
Hard

Contracts and recovery

Line 19 of CornShirtTicket.sol: external versus onlyRole(MINTER_ROLE)?
external exposes an entry point; onlyRole authorizes the caller. External visibility does not mean unrestricted completion.
Why use require at Marketplace lines 64–74?
Each condition is a mandatory invariant. False must revert all state. Plain if/else does not fail unless its invalid branch explicitly reverts.
What if safeTransferFrom fails after lines 134–135 update state?
The whole transaction reverts, including processedPayments = true and active = false. Solidity transaction state is atomic.
Why not automatically refund when database finalization fails after NFT movement?
The buyer may already own the NFT. Immediate refund could give the buyer both asset and money. Recovery first reconciles ownerOf, stored hashes, and operation state.
36
Defence

Architecture questions

Why are Supabase ownership and ownerOf both needed?
Supabase is operational/searchable truth; ERC-721 is token-ownership truth. Sensitive operations compare them and block mismatches for reconciliation.
Why does finalization belong in a PostgreSQL RPC?
Ticket, inventory, operation, transaction, QR, listing, or proceeds changes must commit together. Separate server writes could leave partial state.
What principle connects the entire project?
The browser is never proof. Trusted routes verify identity, database rules, exact provider results, and blockchain receipts; durable state makes retries safe.
What is the managed-wallet prototype limitation?
The server controls encrypted customer signing keys. This enables coordinated flows but makes server secret protection and platform trust critical; some transfer policy is application-level rather than enforced in the NFT contract.
